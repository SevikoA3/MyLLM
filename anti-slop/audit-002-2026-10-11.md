# Attachment maintenance audit

11 October 2026. Phase 17 maintenance. Anti Slop mode: during.

Reading this as: an Android chat composer for people using custom endpoints, following MyLLM's existing dark operational design. ENERGY 1 / RHYTHM 1 / MOTION 1.

## Result and reasons

- The attachment action opens the system Files picker because both documents and images must be reachable from one action.
- Images retain thumbnails; documents use the existing platform document symbol and their filename because binary documents cannot be rendered as images.
- X sits over the preview's top-right corner because removal belongs to that attachment. Its visual background preserves contrast over photos, while its target remains 44 dp.
- Existing tokens define colors, typography, spacing, and radii. Filename labels use the data face to match other technical values.
- Document metadata uses the same private staging directory and conversation JSON shape as existing images. No database migration or dependency change is needed.
- Limits are the owner's explicit choice: 10 attachments, 10 MB per file, 80 MB combined. Count and bytes are validated before staging; actual sizes are checked again before Base64 encoding.

## Endpoint and protocol evidence

Authenticated `GET /models` using local `AMANAI_ENDPOINT` and `AMANAI_KEY` returned HTTP 200 and 60 records. Of those records, 39 declared `image`, and 24 declared `file` in `input_modalities`. File-capable records reported `file_processing: text_extraction`. Credentials and response content were not logged; only catalog capability metadata was inspected.

| Protocol | Image mapping | Document mapping |
|---|---|---|
| Responses | `input_image` with `image_url` | `input_file` with `filename` and `file_data` |
| Chat Completions | `image_url` with nested `url` | PDF only, `file` with nested `filename` and `file_data` |
| Auto | Uses Responses for attachment requests | Uses Responses for attachment requests |

The app uses model-declared modalities or the existing explicit model override. Missing declarations do not enable attachment selection. Unsupported historical attachments block sending with recovery copy instead of being dropped. No billable capability probing was performed.

The request shapes and supported document categories follow [OpenAI's file-input documentation](https://developers.openai.com/api/docs/guides/file-inputs) and [image-input documentation](https://developers.openai.com/api/docs/guides/images-vision). The picker uses the installed package, with `copyToCacheDirectory: true` as described by [Expo DocumentPicker](https://docs.expo.dev/versions/latest/sdk/document-picker/).

## Remaining manual checks

Native Files providers, cancellation/back behavior, large filenames and font scaling, TalkBack, physical keyboard focus, and native overlay geometry require the owner to test on Android. Real file/image generation was not requested as a billable smoke test.

The 80 MB limit is an app limit. Providers and model context can impose lower limits. Base64 expands 80 MB of source data to about 107 MB before JSON/request copies; memory behavior at that limit remains unmeasured on the phone. Existing conservative context estimation can reject large attachments before sending.
